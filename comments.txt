Phase #8 — Authorization validation result

The additional checks confirm the behavior very clearly.

1. Request without Authorization token
Result: HTTP 401
Response: CRAPIResponse(message=Invalid Token, status=401)

This confirms that authentication is enforced. An unauthenticated user cannot access the endpoint.

2. Request with user X token + random/nonexistent vehicle ID
Result: HTTP 404
Response:
{"message":"Sorry we didn't get vehicle for user: ","status":0}

This confirms that the API distinguishes between:
- an unauthenticated request -> 401
- an authenticated request for a nonexistent vehicle -> 404
- an authenticated request from user X for user Y's valid vehicle -> 200 with Y's data

That comparison makes the authorization flaw much stronger.

Confirmed finding:
Broken Object Level Authorization (BOLA) / IDOR-style authorization weakness on:
GET /identity/api/v2/vehicle/{vehicleId}/location

Why this is BOLA:
The server correctly authenticates user X, but when X supplies a valid vehicle identifier belonging to user Y, the API returns Y's vehicle/location object instead of checking ownership and rejecting the request.

Expected secure behavior:
After identifying user X from the Bearer token, the backend should verify that the requested vehicle belongs to X. If it belongs to another user, it should normally return 403 Forbidden (or a deliberately chosen 404 if the application uses object-hiding behavior).

Actual behavior:
X token + Y vehicle ID -> HTTP 200 + Y's location, name and email.

This gives us a clean three-way proof:
A. No token -> 401
B. X token + nonexistent vehicle -> 404
C. X token + Y's valid vehicle -> 200 + Y's protected data

Impact:
A logged-in user who obtains another valid vehicle identifier can access that vehicle owner's location information and associated identity data. The exposed response includes precise latitude/longitude, full name, email address and vehicle ID.

For learning purposes, notice that the UUID itself is not the vulnerability. UUIDs may be difficult to guess, but object identifiers must never be treated as authorization controls. The vulnerability exists because the backend trusts the supplied object reference without confirming ownership.

At this point the core vulnerability is confirmed. Do not enumerate many vehicle IDs; that would add little technical value to the finding.

Next step for Phase #8:
We should now inspect one or two closely related vehicle endpoints to determine whether this authorization weakness is isolated to /location or is part of a broader object-authorization pattern. Keep the same human-driven method: one controlled cross-user test at a time, compare expected vs actual behavior, and record the evidence.

Additional Phase #8 finding — Cross-user mechanic report access

You tested:

GET /workshop/api/mechanic/mechanic_report?report_id=8

while authenticated as user Y. The JWT payload confirms the subject is:

test.userY@email.com

The API still returned HTTP 200 and disclosed report 8, which belongs to user X. The response includes:
- report ID: 8
- mechanic identity
- vehicle internal ID
- VIN
- owner email: test.userX@email.com
- owner phone number
- problem details
- report status and timestamps

This is another confirmed Broken Object Level Authorization (BOLA) / IDOR-style finding.

Why this matters:
The application authenticates user Y successfully, but the backend appears to trust the user-controlled report_id parameter without verifying that report 8 belongs to Y or that Y is otherwise authorized to read it.

Expected secure behavior:
The server should authorize access to the specific mechanic report after authentication. If report 8 belongs to user X and Y has no legitimate relationship to it, the API should reject the request, typically with 403 or an intentionally non-revealing 404.

Actual behavior:
Y token + X's valid report_id=8 -> HTTP 200 + X's report data.

This also tells us something important about the scope of Phase #8: the authorization weakness is not limited to the vehicle-location endpoint. We now have cross-user object access in at least two different API areas:
1. /identity/api/v2/vehicle/{vehicleId}/location
2. /workshop/api/mechanic/mechanic_report?report_id={id}

The identifier style is different:
- vehicle location uses a UUID-like vehicle identifier
- mechanic report uses a simple numeric report_id

But the underlying security failure is the same: the server retrieves the object based on a client-supplied identifier without enforcing object-level ownership/authorization.

The numeric report_id makes this especially important from a design perspective because sequential identifiers are often easier to discover than UUIDs. The issue is still authorization failure—not the fact that the ID is numeric.

For now, do not enumerate a range of report IDs. One controlled cross-user proof is enough to confirm the flaw.

Next useful validation:
1. Request report_id=8 without a token and record the status.
2. With Y's token, request one obviously nonexistent report ID and record the status.
3. If both behave as expected, we can document this as a second clean BOLA finding and then continue checking only a small number of distinct object types in Phase #8 rather than repeatedly testing the same pattern.

Additional Phase #8 finding — User Y can create a mechanic report for user X's vehicle

You tested:

POST /workshop/api/merchant/contact_mechanic

while authenticated as user Y, but supplied user X's VIN:

R1J9FDW628RCR6U74

The API returned HTTP 200 and created report ID 10 successfully.

The response confirms:
- sent: true
- report_id: 10
- report link was generated

You also observed that the newly created report appears in user X's dashboard because the VIN belongs to X.

This is important because it is not just unauthorized data reading. It is an unauthorized cross-user action that changes application state for another user's object.

Security interpretation:
This is another object-level authorization failure. The backend accepts the VIN from user Y and performs the mechanic-contact workflow without verifying that Y owns or is authorized to act on that vehicle.

Expected secure behavior:
After authenticating Y, the backend should verify that the supplied VIN belongs to Y or that Y has explicit authorization to act on that vehicle. If the VIN belongs to X, the request should be rejected.

Actual behavior:
Y token + X VIN -> HTTP 200 -> mechanic report created for X's vehicle.

Potential impact:
An authenticated user who learns another valid VIN may be able to create unwanted service/mechanic requests associated with another user's vehicle. Depending on downstream workflow, this could cause:
- unauthorized state changes
- unwanted mechanic interactions
- misleading service history
- nuisance or workflow abuse
- potential integrity impact on another user's account/vehicle records

This is stronger than a read-only BOLA because it demonstrates unauthorized modification/action against another user's object.

Your follow-up validation for the mechanic-report read endpoint is also useful:

A. No token
Result: HTTP 401 Unauthorized
Response:
{"message":"JWT Token required!"}

B. Authenticated request for nonexistent report
Result: HTTP 400 Bad Request
Response:
{"message":"The Report does not exist for given report_id."}

C. Y token + X valid report
Result: HTTP 200 + X's report data

That gives us another clear authorization comparison:
- unauthenticated -> denied
- authenticated + nonexistent object -> not found/error
- authenticated + another user's valid object -> allowed

So Phase #8 now has at least three concrete authorization failures:
1. Cross-user vehicle location disclosure
2. Cross-user mechanic report disclosure
3. Cross-user mechanic report creation using another user's VIN

Important learning point:
These are related but not identical findings. The first two are unauthorized reads. The third is an unauthorized action/state change. When we document Phase #8 later, it may be useful to group them under a broader object-level authorization weakness while still recording each affected endpoint and impact separately.

My suggestion for the next step:
Do not keep testing endless variations of these same endpoints. We already have enough evidence that object-level authorization is broadly weak.

Move to one different object/action area and perform a single controlled X-vs-Y ownership check. If the same pattern appears again, that is enough to establish this as a systemic authorization issue across the application rather than an isolated bug.

Also, for this contact_mechanic endpoint, one small negative test would be useful before moving on:
- with Y's valid token, send one obviously nonexistent/random VIN and record the status/response

Why:
That helps distinguish “valid foreign object accepted” from “backend accepts any arbitrary VIN,” which are different failure modes.
